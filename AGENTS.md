## Cursor Cloud specific instructions

This is a Next.js 16 (App Router, React 19, Tailwind 4) recipe app that uses Supabase
as its database, intended to deploy on Vercel. Standard scripts live in `package.json`
(`dev`, `build`, `start`, `lint`).

### Automated environment (`.cursor/environment.json`)

On Cloud Agent boot the environment is provisioned automatically — you normally do **not**
need to run any of the setup below by hand:

- `install` → `.cursor/cloud/install.sh`: installs Docker CE (pinned 28.x, DinD-compatible),
  the Supabase CLI (`.deb`), Node deps (`npm install`) and Playwright browsers
  (`npx playwright install --with-deps`). Idempotent — safe to re-run.
- `start` → `.cursor/cloud/start.sh`: launches `dockerd`, runs `supabase start` (applies
  `supabase/migrations/`), and writes `.env.local` from `supabase status`.
- `terminals`: a `web` terminal running `npm run dev` (http://localhost:3000).

### Services

- **Web app (Next.js)**: `npm run dev` (http://localhost:3000). Requires Supabase to be
  configured (`.env.local`) and running — `/` and `/recipes` redirect to `/login` and the
  recipes list reads an RLS-protected `recipes` table, so the DB must be up to exercise it.
- **Database (Supabase, local stack)**: Postgres + REST + Auth in Docker. API at
  `http://127.0.0.1:54321`, Studio at `http://127.0.0.1:54323`.

### Non-obvious caveats

- **Docker needs the `docker` group.** `dockerd` runs as root with the socket owned
  `root:docker`; a shell must be in the `docker` group. Group membership only applies to
  new shells, so wrap ad-hoc commands as `sg docker -c "docker ..."` / `sg docker -c "supabase ..."`.
- **`dockerd` is not managed by systemd/`service`** in this VM — `start.sh` launches it
  directly (`sudo dockerd`) and waits for readiness. Logs: `/tmp/dockerd.log`.
- **Docker must stay on 28.x.** Docker 29 defaults to the containerd snapshotter, which
  breaks the `fuse-overlayfs` storage driver this nested VM requires.
- **`.env.local` is git-ignored** and regenerated by `start.sh`; for the default local
  stack the anon key is the standard `supabase-demo` demo key.
- **The auth flow needs a real user.** There is no signup UI — create a confirmed user via
  the admin API (`POST /auth/v1/admin/users` with the `service_role` key and
  `"email_confirm": true`).
- **`service_role` can't touch `recipes` via REST.** Migrations only `grant` to
  `authenticated`, so seed rows with `docker exec -i supabase_db_workspace psql -U postgres -d postgres`
  (bypasses grants + RLS) rather than the REST API.
- New tables need explicit `grant` for `anon`/`authenticated` in the migration in addition
  to RLS policies, otherwise the REST API returns `permission denied`.
- `supabase db reset` re-applies all migrations from scratch (use after editing SQL).

### Tests

- **Unit tests (Vitest)**: `npm run test:unit` — no extra setup, runs against `src/lib/`.
- **E2E tests (Playwright)**: `npm run test:e2e` — requires Supabase + `npm run dev` running.
  Full procedure: see `.cursor/skills/run-tests/SKILL.md`.
- Key E2E constraints:
  - Tests run with `workers: 1` (sequential) to avoid storageState race conditions.
  - Test users use timestamped emails (`e2e-{ts}-{role}@example.com`) to avoid Supabase
    Auth rate limiting on repeated create/delete of the same email.
  - `signOut()` must use `scope: 'local'` in `src/app/recipes/actions.ts` to avoid
    global session invalidation that breaks subsequent authenticated tests.
  - Recipe cleanup uses psql (DELETE grant not yet in migrations — added with #7).

### Next.js 16 gotchas

- `cookies()`/`headers()` are async — `src/lib/supabase/server.ts` awaits `cookies()`.
- Middleware is renamed to `proxy` (use `proxy.ts`), not `middleware.ts`.
